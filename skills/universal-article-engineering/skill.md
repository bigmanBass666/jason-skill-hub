# Universal Article Engineering Skill

> 一段真实的探索已经发生。它有价值。这个 Skill 的任务，是把它如实还原成一段读者能完整体验的认知旅程。

---

## 全局流程

```
Phase 1 挖掘  →  Phase 2 找脊梁  →  Phase 3 重建  →  Phase 4 写作  →  Phase 5 归档
从素材提炼价值      确定核心主线        组织叙事顺序        表达与风格        集中存储+软连接
```

---

## Phase 1 — 挖掘：从原始素材里找什么

不是所有发生过的事都值得进文章。从对话记录、报错、代码、决策里识别高价值时刻。

### 值得保留的时刻

- **第一次遭遇异常** — 哪一刻意识到"这不对劲"？
- **错误的方向** — 追了一条错路然后发现自己错了。这往往比走通的路更有叙事价值
- **真正的转折点** — 理解发生了根本性改变的那一刻
- **自己也感到意外的发现** — 当时觉得"等等，这怎么可能"，读者也会有同感
- **有价值的死路** — 没走通，但排除了重要可能性，或揭示了更深的结构
- **因果链闭合的瞬间** — 所有线索突然连在一起的那一刻
- **对话中的转折** — 调查过程中，另一方的一句提问或质疑改变了方向。这种时刻在协作探索里极为常见，也极有叙事价值。原话优先，不要转述

### 死路的写法

死路不是"这条路不行"三个字。死路的价值在于它揭示了什么——为什么在当时看起来合理，为什么最终失败，失败的方式如何指向了真正的根因。

❌ `方向一：符号链接补路径。能跑了，但安全风险，治标不治本。`

✅
```
我把 .trae-cn 里的 Node 符号链接指向了系统安装的 Node。

能跑了。

但这只是给一条路铺了地砖。其他几十个工具呢？
PATH 还是只有三个 .trae-cn 路径。

问题根本没有被碰到。
```

死路写法的核心：**让读者亲眼看到它为什么不够**，而不是被告知结论。

### 判断是否值得保留

- 这个时刻改变了方向或理解吗？
- 这打破了某个原本以为成立的假设吗？
- 这很容易被忽视，但其实关键吗？
- 这对读者来说会是意外吗？

### 可以丢弃的

- 重复尝试同一方向、没有新信息
- 纯机械性操作（安装、等待、配置）
- 通往死路但没有揭示任何东西的岔路
- 技术细节本身，如果它不推进理解

## Phase 2 — 找脊梁：文章的核心主线

脊梁不是"发生了什么"，而是**读者的理解是如何被改变的**。

### 找法

从两个端点出发：

```
起点：我（和读者）最初以为世界是什么样的？
终点：我现在知道世界实际上是什么样的？
```

脊梁是连接这两个状态的路径。帮助读者走这条路的内容留下，不在这条路上的切掉。

### 脊梁的常见形态

| 类型 | 脊梁结构 |
|------|----------|
| **调查溯源** | 异常 → 错误假设 → 真正根因 → 工程意义 |
| **挑战现状** | 主流认知 → 反例 → 更深的真相 → 影响 |
| **发现洞察** | 普通现象 → 隐藏规律 → 为什么重要 |
| **解法呈现** | 问题有多难 → 常规思路为何失败 → 真正解法 |

## Phase 3 — 重建：组织叙事顺序

真实发生的顺序不等于最好的叙事顺序。重建是忠实地还原，不是捏造。

### 核心原则

**从最有冲击力的异常开始，不从会话开始的地方开始。**

读者不需要看到你怎么打开终端。他们需要在第一段就感受到异常的存在。

**压缩 vs 展开**

- 长时间的重复尝试 → 一句话带过
- 关键转折的30秒 → 可以展开成整节
- 死路 → 保留结论，省略过程；除非死路本身有叙事价值

**转折时刻需要自己的空间。**

调查里真正改变方向的那一刻——一句提问、一个数据、一行代码——不能被压缩成过渡句夹在两段之间。它需要停下来，让读者感受到它的重量。

```
（前文：两个失败方案刚被放弃）

用户说了一句话：

"别再等别人了，也别搞什么治标不治本的了，直接从最底层开始解决！"

好。那就从最底层开始。
```

一句话独占三行。前后各留白。这是转折时刻的正确处理，不是段落里的一个句子。

**时间顺序可以重排，因果关系不能篡改。**

可以把第三天发现的线索放到第一天叙述，前提是它属于同一条逻辑链。不能颠倒因果，不能让后发现的事看起来导致了先发现的事。

### 忠实的边界

| 可以 | 不可以 |
|------|--------|
| 压缩时间 | 添加没有发生过的发现 |
| 重排顺序 | 删除影响最终结论的失败 |
| 省略不相关细节 | 夸大确定性（当时有疑问就应该有疑问） |
| 补充读者需要的背景 | 让走过的死路消失得好像从未存在 |

## Phase 4 — 写作：让叙事真正可读

### 写作原则

#### 1. 永远不要直接进入技术细节

❌ `这是 Electron 的 env 继承问题。`

✅
```
我只是执行了一次 node --version。

结果：command not found。
```

> 先让读者感受到异常，再进入解释。

---

#### 2. 进入现场 + 适度情绪

文章应该像调查录像，不是结论报告。让读者看到：终端、报错、推理、怀疑、验证。

情绪是节奏的一部分：

```
我愣了一下。因为这不合理。
这一刻，我意识到问题不在系统层。
我已经准备放弃了。
```

---

#### 3. 延迟揭露（认知闭环驱动）

```
现象 → 异常 → 怀疑 → 局部验证 → 更大异常 → 真正根因
```

不要一开始就给答案。读者的大脑会自动继续往下读。

---

#### 4. 技术文章必须有"层"

优秀技术文章不是平铺，而是不断向下挖：

```
第一层：表面现象
第二层：系统行为
第三层：架构异常
第四层：源码逻辑
第五层：底层机制
第六层：真正根因
第七层：设计缺陷
第八层：工程意义
```

---

#### 5. 高潮必须被放大

关键发现处，放慢节奏：

❌ `然后我发现了 preserve-env。`

✅
```
直到我在混淆源码里。

看到了一行几乎没人注意过的配置：

"preserve-env": { type: "boolean" }

我停住了。
```

---

#### 6. 构建完整因果链

```
GUI 启动
↓
userEnv = undefined
↓
PATH 消失
↓
Prepend 创建新 PATH
↓
fork() 替换继承
↓
Extension Host 永久损坏
```

> 必须让问题能够被"脑内重演"。

---

#### 7. 两种驱动读者的燃料

**Interesting** — 跟着自己的好奇心走。你觉得无聊的部分，读者也觉得无聊，跳过它。这决定**选什么写**。

**Surprising** — 打破读者预期。这决定**怎么呈现**：

```
AI Agent 正常。Extension Host 坏了。
UI 正常。PATH 已经死亡。
```

---

#### 8. 主动管理读者的怀疑

技术读者会质疑每一个声明。抢先说出他们心里的疑问：

❌ `所以 Extension Host 的 PATH 被破坏了。`

✅
```
你可能会想：PATH 怎么可能在 UI 正常的情况下悄悄消失？

我当时也不信。直到我在两个进程里分别打出环境变量——
```

---

#### 9. 结尾两阶段：收束 → 升华

```
根因已经确认。                        ← 收束

但真正让我担心的，是这类问题的普遍性。    ← 推演

很多 Bug 都不是程序崩了。

更危险的是。

它看起来还能运行。                     ← 升华
```

#### 10. 不要在结尾切换格式

文章建立了调查纪录片的气质之后，结尾最常见的错误是：突然切换成 FAQ、问答列表、或技术索引表。

```
## 几件事

### 为什么这个问题存在？
...
### 为什么没人发现？
...
### 和之前方案对比
...
```

这种格式会把读者从"沉浸在调查里"瞬间拉回"在看文档"。

这些内容本身有价值，但形式错了。应该把它们织回叙事里：

❌ `### 为什么这个问题存在？`
`这不是 Bug。这是设计选择。`

✅
```
整个调查最让我意外的，不是根因本身。

而是它为什么一直没被发现。

Extension Host 的 PATH 是残缺的——但 AI Agent 进程有自己的修复机制，会在运行时重新注入 PATH。所以在 Agent 终端里，一切看起来正常。

它看起来能正常运行。这才是最危险的一类问题。
```

> 反思、对比、背景——全部可以保留，但要用叙事语气说出来，不要用标题把它们打成条目。

---

### 视角规范

这一视角的根本优势：**不是在扮演一个角色，而是在如实报告自己真实的经历。** 这是真实性的来源，不需要表演。

语气：冷静、理性、观察感、进程视角。允许真实的认知状态变化，不过度拟人。

**强沉浸感句式（高频使用）：**

> `我继续向下追。` / `我开始意识到。` / `这一刻。` / `问题终于闭环。` / `我停住了。` / `代码一定会留下痕迹。`

---

### 标题原则

**策略 A：调查感**（适合 RE、故障溯源、深挖类）

```
我花了 6 小时逆向 XXX，终于找到真正原因
为什么 XXX 会失效？我扒开 2MB 混淆源码后发现了真相
```

**策略 B：简短 + 制造疑问**（适合洞察类、发现类）

5 词以内，以"我"开头，留下读者必须点进去的问题：

```
我发现了一个新超能力
我终于理解了 XXX
```

---

### 视觉结构

大量留白、短段落、多层标题、代码块、因果链箭头、表格。

> 可读性本质上是视觉节奏。

## Phase 5 — 输出与归档：文章的落地位置

所有通过本 Skill 创建的文章，统一归档到集中目录，由环境变量控制。

### 环境变量

```
ARTICLES_PATH = D:\working\articles   （用户级环境变量）
```

- 读取方式：`$env:ARTICLES_PATH`（PowerShell）或 `$ARTICLES_PATH`（bash）
- 目录不存在时自动创建：`mkdir -p "$env:ARTICLES_PATH"`

### 输出规则

1. **文章正文** 写入 `$env:ARTICLES_PATH/<文件名>.md`
2. **在源项目目录** 创建符号链接指向集中目录的文件，方便在项目上下文中也能访问：
   ```
   # PowerShell（管理员或开发者模式下）
   New-Item -ItemType SymbolicLink -Path "<项目目录>/<文件名>.md" -Target "$env:ARTICLES_PATH\<文件名>.md"
   ```
3. 如果源项目已有同名文件（非符号链接），先备份再创建链接

### 文件命名

- 使用 kebab-case，简短描述主题：`why-path-disappeared.md`、`reverse-engineering-cpe.md`
- 避免日期前缀（由 git 管理历史）

### 归档流程（写完文章后自动执行）

```
写入正文到 $ARTICLES_PATH/<name>.md
    ↓
在当前项目目录创建符号链接
    ↓
告知用户两个路径
```
